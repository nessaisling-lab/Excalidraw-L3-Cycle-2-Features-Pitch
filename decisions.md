# decisions.md — Persistent Save (C1 First-Save Moment)

Running log of every decision made on this build: what was decided, who made the call, and why. This is the team's working reference — kept in the repo, not the PRD, so it's easy to grep and diff alongside the code it governs.

The PRD (`persistent-save-master-prd.md`) states final requirements only. This file is where the reasoning and history live. When the two ever seem to disagree, the PRD wins for what to build; this file explains why it says what it says.

**Maintainers:** whole team. Append, don't rewrite history — if a decision changes, add a new row noting the supersession rather than editing the old one.

| 2026-09-17 | **Supersedes 2026-09-16 entry above.** Persistent save button is **prototype quality this cycle**, not production standard. Build bar: reliable enough that test users don't hit bugs that contaminate activation data; settings persistence and full edge-case hardening explicitly out of scope. If the button moves the save number, it gets properly spec'd next cycle, with this prototype's learnings feeding that spec. This resolves the earlier discrepancy between the PRD (still pending) and Aisling's engineering notes (reported as already resolved via team sync) — Carlos's direct written answer is authoritative |
| 2026-09-16 | A successful save suppresses only the First-Save Moment prompt; the persistent button and tooltips remain visible, unaffected by save state | Team, at engineering sync | The prompt is a one-time nudge; the button and tooltips serve an ongoing, independent role regardless of whether the user has already saved once |
| 2026-09-16 | First-visit definition finalized: dedicated local `excalidraw-c1` record determines first-time status, not autosave presence. Private/incognito = new visitor. Multiple tabs share storage and a `storage` event listener suppresses duplicate prompts across tabs | Team, at engineering sync | Autosave writes within seconds, so without a dedicated record a same-session reload would look like a returning visitor and the prompt would never fire |
| 2026-09-16 | Event vocabulary adopted: `session_start`, `first_element_placed`, `prompt_shown`, `prompt_dismissed`, `save_action` (fields: `method`, `entry_point`), `plus_link_click`. A save counts only when it succeeds — never on `AbortError` | Team, at engineering sync | Existing `trackAction` fires before a save completes, which would over-count canceled saves; success-gating fixes this. One shared vocabulary serves the prompt, button, and tooltips alike. **Note 2026-09-18: `plus_link_click` now has no event source, since the Plus link is excluded from the prompt entirely — flagged below, not yet resolved whether to remove or keep dormant** |
| 2026-09-16 | Accessibility acceptance criteria finalized at WCAG 2.1 AA with testable pass conditions — contrast (4.5:1 text / 3:1 controls), 44×44px targets, scoped Escape behavior (dismisses only when focus is inside the prompt; visible ✕ always works), single polite screen-reader announcement, tooltip keyboard behavior | Team, ratified by Jill and Carlos | Closes the previously under-specified accessibility gap with concrete, checkable criteria instead of directional intent (R12) |
| 2026-09-16 | Copy ownership confirmed: Lawrence writes prompt copy and screen-reader announcement text as one task; tested in Jill's Round 0 Lyssna study before the stage 1 build is finalized | Team | Copy-writing and accessibility wording are the same underlying task; Lawrence's existing scope (copy review, client correspondence) made him the natural single owner |
